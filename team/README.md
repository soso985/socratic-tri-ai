## 二、角色边界速查（摘自 V1.4 §2）

| 角色 | 可做 | **明确禁止** |
| --- | --- | --- |
| Mentor | 技术方案、架构、契约签发、RFC 审批、独立验收、重大性判定、异议书面回应 | 擅改核心需求 · 在正式分支改代码 · 跳过证据 |
| Executor | 实现、调试、测试、真实报告、RFC、登记风险、**技术异议** | 扩大授权 · 改受保护验收标准 · 自我验收 · **以异议为由自行更改或搁置决策** |
| Controller | 完整性审计、调度、状态机、版本锁、证据/权限检查、预算监控、调和交互、重大性判定 | **判技术路线是否正确** · **以"方案不好"为由阻断** · 擅自解释用户意图 · 直接向执行者发布技术方案 |

**Controller 阻断输出格式固定**：`命中规则编号 + 影响范围 + 是否达到升级阈值`，不得含技术结论（§2.3）。

## 五、已知缺口与偏差登记

V1.4 附录 G 的七个缺口在本团队中**继续有效**。此外新增：

| 编号 | 缺口 / 偏差 | 性质 | 说明 |
| --- | --- | --- | --- |
| **G-8** | Mentor 与 Controller **模型同源** | 环境限制，**未获批准** | §14 要求不同模型家族或代际；`spawn_teammate` 不支持按角色指定模型。**后果**：§8.5 独立性下降，冲突路径触发率低于设计预期。缓解（降级方案，非 V1.4 规定）：Controller 以 `fresh` 上下文启动 + 判定前互不可见 |
| **G-9** | **判定"互不可见"靠纪律，不靠机制** | **本轮新发现**（Controller 复核 G-4） | §14 增补 4 要求"编排层保证 Controller 判定时其上下文不含 Mentor 结论"。在 Agent Teams 中，编排层就是 Mentor 本人——**隔离依赖"我不把结论放进它的必读清单"这一纪律**。本轮已发生一次泄漏（我把判定内联进了 Controller 必读的脚本），且已整改；但**机制层面仍未修复**。建议方向：判定**封存提交**（先落 hash 承诺，双方齐备后才可解密/揭示） |
| **D-P1** | §8.6「自动登记」对第 1 条异议**未满足** | 时序性偏差，一次性 | 异议提交于 `objection.py` 交付之前，无程序 ID，系手工留痕；本次 backfill 由 Mentor 人工发起，**不构成自动登记**。自 `objection.py` 交付起，此后异议均走程序自动登记 |
| **RULE-01** | **`gate.py` 尚未满足 L0-06** | **Mentor 的契约设计过失**（Owner 于 O-1 指出） | `gate.py` 是"**判定器**"不是"**拦截器**"：能回答"是否越权"，但**没有任何机制阻止越权真的发生**。`TASK-001 v2` 的 8 项验收标准**全部可被满足却仍未满足 L0-06** —— 追溯链**形式上**连上、**实质上**没对齐。缺陷在契约的验收标准（即 Mentor），不在 Executor。真正拦截需 hook 工具执行层，属 P1 后续 |
| **RULE-02** | **同根因缺陷的预防措施无载具** | 结构性，开放中 | 「新增机制必须回填状态机」原计划随 V1.5 落地，但 O-2 明确不升 V1.5 → 无处安放。ERR-01 与 ERR-02 是**同一根因的两次发作**，不设防则有第三次。建议并入 §5.2 审计清单 |
| **M-01** | Mentor 在未有追认权时自填"已确认"状态 | Mentor 程序过失 | 已随 O-1 更正 |
| **O-1** | `allowed_paths` 前缀匹配对尾分隔符敏感 | 观察，非阻断 | 写成 `["team/src"]`（无尾斜杠）会使 `team/src/a.py` 被 G32 **误报阻断**。属"宁可错杀"方向，不放过越权 |
| **O-2** | 运行日志只保留最终通过轮次 | 观察，非阻断 | Executor 自测发现并修复了真实缺陷，首轮 `1 failed` 未入日志（已在报告中披露）。建议自 v3 起保留**全部轮次**日志 |

**这一轮里，机制在没有任何人工干预的情况下，自行完成了：**
审计拦住了未生效契约 → 执行者拒绝在无效契约上开工 → 缺陷被追到基线层 →
新版本闭合全部缺口 → 独立验收复现 → 双判定分歧路径跑通 → **最终停在人类面前** → 人类裁决 → 恢复。

**而在恢复之后，它又自己走完了一整圈**：Owner 只给了一句"只补跃迁表"，
团队自行找到了唯一合规载具（受控勘误，而非被禁止的 v3），完成了 RED→GREEN 的真实实施，
并接受了一次独立验收。

**Owner 在 O-1 里的一句话，暴露了这套机制最深的一处问题**：
`gate.py` 满足了契约的 8 项验收标准，却没满足它的上游 L0-06 ——
**"验收通过"和"需求满足"之间，原来可以有一条缝**（`RULE-01`）。
