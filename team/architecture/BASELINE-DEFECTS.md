## V1.4-ERR-01 · §8.4 与 §10.1 的状态跃迁矛盾

**严重度**：中（导致实现层无法自洽，但不是安全问题）

### 缺陷描述

| 条款 | 原文要点 |
| --- | --- |
| V1.4 **§8.4**（次数口径第 3 项） | 「**异议提交即任务进入 BLOCKED**（§10.1）」 |
| V1.4 **§10.1** 合法跃迁 | `DRAFT→AUDITING→READY→RUNNING→SUBMITTED→ACCEPTED`；<br>`RUNNING\|SUBMITTED → REWORK\|BLOCKED\|CHANGE_PENDING\|ESCALATED`；<br>`CHANGE_PENDING → READY`（经新版本） |

**矛盾**：`BLOCKED` 只能从 `RUNNING` 或 `SUBMITTED` 进入。
而 §8.4 允许异议在**任何时点**提出——包括任务处于 `DRAFT` / `AUDITING` / `READY` 时
（尤其是"契约前提有问题"型异议，本质就发生在执行之前）。

此时"异议提交即进入 BLOCKED"会构成**非法跃迁**，与 §10.1 直接冲突；
若严格按 §10.1 执行，则**启动期的异议无法使任务停下**，§8.4 的保护落空。

### 根因

§10.1 的跃迁表是按**执行生命周期**写的，成文时未预见「异议可在执行前提出」这一情形。
§8.4 在 V1.4 中新增了启动期异议，但没有同步修订 §10.1。

### Mentor 的技术处置（本团队内生效，非基线修订）

在 `TASK-001-v2` 中采用如下解释，并将其写入契约的跃迁表：

> 在 §10.1 原有跃迁集合之外，**追加**：
> - `DRAFT | AUDITING | READY → BLOCKED`（事由：异议提交，§8.4）
> - `BLOCKED → <进入 BLOCKED 前的状态>`（事由：异议处置完毕且原决策维持，或解阻条件满足，§9.2）

**理由**：§8.4 的立法意图是"异议一提交，任务就必须停下来"，这是它的全部保护价值所在。
若因跃迁表未列举而使启动期异议无法停机，等于把保护限缩到只对执行期生效——
这与 §8.4 的明文表述相反。故按**立法意图**解释，并登记缺陷待基线正式修订。

### 未决项

- 本处置**只在本团队内生效**，**未修订 V1.4 正文**。
- 建议在 **V1.5** 中正式修订 §10.1，或由 Owner 裁决是否接受本解释。
- 在基线正式修订前，任何引用 §10.1 的实现都必须同时引用本缺陷登记，不得单独引用 §10.1。

## V1.4-ERR-02 · §10.1 状态跃迁表存在死端（REWORK / ESCALATED 无出边）

**严重度**：**高**（任务一旦进入即永久卡死，且会在第一次返工或第一次升级时必然触发）

### 缺陷描述

V1.4 §10.1 完整的跃迁集合为：

```
DRAFT → AUDITING → READY → RUNNING → SUBMITTED → ACCEPTED
RUNNING | SUBMITTED → REWORK | BLOCKED | CHANGE_PENDING | ESCALATED
CHANGE_PENDING → READY（经新版本）
```

由此可得：

| 状态 | 出边 | 判断 |
| --- | --- | --- |
| `CHANGE_PENDING` | → `READY` | 正常 |
| `BLOCKED` | 无（V1.4 原文） | **死端** → 已由 `V1.4-ERR-01` 的处置补齐 |
| **`REWORK`** | **无** | **死端** |
| **`ESCALATED`** | **无** | **死端** |
| `ACCEPTED` | 无 | 正确（终态） |

**后果**：
- `REWORK`（§9.2「给出明确失败项与受限返工契约，重新验收」）——返工完成后**无法回到 `RUNNING`**，
  §9.3 的返工与回归流程在状态机上不可执行。
- `ESCALATED`（§9.2「进入用户决策」）——用户裁决后**无法回到任何可执行状态**，
  §6 两级决策的产出无处落地。

这不是边界情形：**第一次返工、第一次升级就会必然撞上。**

### 根因

§10.1 成文时按"主流水线 + 异常分支"写，异常分支只补了 `CHANGE_PENDING → READY` 一条回归路径
（因为它对应"新版本契约"这一明确出口），而 `REWORK` 与 `ESCALATED` 的回归条件写在 §9.2/§9.3/§6，
**却忘了同步补进状态机**。与 `V1.4-ERR-01` 同源：**新增机制时未回填状态机。**

### 发现与确认

- 发现者：**Executor**（工作报告风险 R-1）
- 独立复现者：**Mentor**（`evidence/mentor-verify-TASK-001.py`，构造 `REWORK→RUNNING` 与
  `ESCALATED→READY`，两者均被 G36 判非法）

### Mentor 的技术处置

在 **`TASK-001 v3`** 中补齐：

| 来源 | 目标 | 事由 |
| --- | --- | --- |
| `REWORK` | `RUNNING` | 返工完成，重新进入执行（§9.2、§9.3） |
| `ESCALATED` | `READY` | 用户裁决「继续」（§6.1、§9.2） |
| `ESCALATED` | `BLOCKED` | 用户裁决「暂停/需补充条件」（§6.5、§9.2） |

### 未决项

- 与 ERR-01 同：本处置**只在本团队内生效**，**未修订 V1.4 正文**。
- **建议在 V1.5 中一并正式修订 §10.1**，并将「新增机制必须回填状态机」写成一条检查项，
  避免第三次同类缺陷。
- 在基线正式修订前，引用 §10.1 的实现必须同时引用本登记。
